# iVolume

A native macOS menu bar app for controlling the playback volume of individual apps, without a
virtual audio driver. It uses Core Audio's process-tap API (macOS 14.2+) to capture each app's
output, scale it by a per-app gain, and hand it back to the real output device.

## How it works

- `MenuBarExtra` (SwiftUI, `.window` style) shows a speaker icon in the menu bar. `LSUIElement`
  keeps the app out of the Dock and app switcher.
- `AudioProcessMonitor` watches `kAudioHardwarePropertyProcessObjectList` and each process's
  `kAudioProcessPropertyIsRunningOutput` via Core Audio property listeners, so the panel's list
  updates the moment an app starts or stops playing audio (no polling).
- `ProcessTap` wraps one app's Core Audio process tap: a private `CATapDescription` for that
  process, a private aggregate device combining the tap with the real output device, and an
  `AudioDeviceIOProcID` that copies each buffer from the tap to the output scaled by that app's
  gain. The gain is read from a lock-free pointer on the real-time IO thread.
- Apps at 100% volume, unmuted, have no tap at all — audio passes through the system mixer
  untouched. A tap is only created once a slider moves off 100% or an app is muted.
- `AudioEngineManager` owns all active taps, rebuilds them when the default output device changes
  (e.g. switching to AirPods), and tears down a tap as soon as `AudioProcessMonitor` reports its
  process is no longer producing output.
- `VolumeStore` persists each app's volume/mute state in `UserDefaults`, keyed by bundle ID (or,
  for bundle-less command-line tools like `afplay`, by executable path).

## Project layout

```
Sources/iVolume/
  App/            App entry point (MenuBarExtra) and NSApplicationDelegate
  AudioEngine/    CAProperty helpers, ProcessTap, AudioEngineManager
  ProcessMonitor/ AudioProcessMonitor
  Persistence/    VolumeStore
  Models/         AudioAppItem
  UI/             MenuBarPanelView, AppRowView
project.yml       XcodeGen project spec
```

The `.xcodeproj` is generated by [XcodeGen](https://github.com/yonaskolb/XcodeGen) from
`project.yml` and is not committed — regenerate it after cloning or after editing `project.yml`.

## Build & run

```sh
brew install xcodegen   # if you don't already have it
xcodegen generate
xcodebuild -project iVolume.xcodeproj -scheme iVolume -configuration Debug build
```

Or open `iVolume.xcodeproj` in Xcode and hit Run. Either way, the build lands in Xcode's
DerivedData under a path that changes per-machine/per-checkout. For everyday use (rather than
active development), copy the built app somewhere stable instead of relaunching it from
DerivedData each time — see "Granting permission" below for why that matters:

```sh
cp -R "$(xcodebuild -project iVolume.xcodeproj -scheme iVolume -configuration Debug -showBuildSettings | awk -F'= ' '/ CODESIGNING_FOLDER_PATH/{print $2; exit}')" /Applications/
open /Applications/iVolume.app
```

## Granting permission

Process taps require the "Audio Recording" permission (declared via
`NSAudioCaptureUsageDescription`). The first time you lower an app's volume below 100% or mute it,
macOS will prompt for this permission. If it's denied or was dismissed, the panel shows a message
telling you to enable it in **System Settings > Privacy & Security > Audio Recording**, then
reopen iVolume.

**This permission grant is tied to the exact signed binary**, not just the bundle ID. The project
signs with `CODE_SIGN_STYLE: Automatic` and no team (`project.yml`), which produces an *ad-hoc*
signature keyed to the literal contents of that build (`codesign -dv` shows `flags=0x2(adhoc)`,
`TeamIdentifier=not set`). Every rebuild changes that hash, so macOS treats it as a brand-new app
and re-prompts for permission — this is why it can seem to "ask every time" during active
development. Two ways to avoid that:
- **Simplest**: don't rebuild. Install once to `/Applications/iVolume.app`, grant permission
  there, and keep using that exact copy. (`tccutil reset AudioCapture com.antonioconopio.iVolume`
  clears out stale grants from prior ad-hoc builds if things get into a confusing state.)
- **For ongoing development**: add a free Apple ID as a Development Team in Xcode's Signing &
  Capabilities tab for the iVolume target (or set `DEVELOPMENT_TEAM: <your team ID>` under
  `settings.base` in `project.yml`). A real certificate-backed signature keeps the same identity
  across rebuilds, so the permission grant survives them too.

## Verifying it works

1. Launch iVolume — you should see a speaker icon in the menu bar and no Dock icon.
2. Play a system sound in a loop so there's something in the list:
   ```sh
   while true; do afplay /System/Library/Sounds/Ping.aiff; done
   ```
   or `say "testing" &` on a loop. The process should appear in the panel within about 2 seconds
   of audio starting.
3. Drag its slider to 50% — the audio should audibly halve in volume; drag it to 0% or tap the
   mute button — it should go silent. Other apps playing audio at the same time are unaffected.
4. Quit iVolume (via the panel's Quit item) and check **Audio MIDI Setup** (or
   `kAudioHardwarePropertyDevices`) — no `iVolume-<pid>` aggregate devices should remain.

### Debug peak-level logging

Set `IVOLUME_DEBUG_LEVELS=1` in the app's environment to have the IOProc log, via `os_log`
(subsystem `com.antonioconopio.iVolume`, category `levels`), the peak sample amplitude of each
tapped buffer before and after gain is applied:

```sh
IVOLUME_DEBUG_LEVELS=1 open ~/Library/Developer/Xcode/DerivedData/iVolume-*/Build/Products/Debug/iVolume.app
log stream --level debug --predicate 'subsystem == "com.antonioconopio.iVolume"'
```

At gain 0.5 you'll see `peakAfter` run at roughly half of `peakBefore`; at gain 0.0, `peakAfter`
is always `0.00000`. This logging path is opt-in only — it's skipped entirely in normal use.
